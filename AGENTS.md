# AGENTS.md — правила для агентов

Проект: Telegram Mini App «Вокруг света за 80 ужинов» (MVP).
Единственный источник требований — `docs/ТЗ Вокруг света за 80 ужинов — Telegram Mini App (MVP).md` (дальше — ТЗ). Если код и ТЗ расходятся, прав ТЗ; если ТЗ неполно или противоречиво — остановись и спроси, не додумывай продуктовые решения.

## Как работаем

- Работа идёт по задачам из раздела ТЗ «План задач для агентов», по одной задаче за сессию. Запуск: `/task <N>` (скилл `.claude/skills/task`).
- Каждая задача — отдельная ветка `task/NN-<slug>` от `main`, один или несколько коммитов. Исполнитель задачи в `main` не коммитит и не мёржит; ветку проверяет и мёржит в `main` оркестратор (fast-forward), см. CLAUDE.md. Пушит только человек.
- Делай только то, что входит в задачу. Замеченные проблемы вне задачи — в раздел «Заметки» `docs/progress.md`, не в код.
- Технические решения, которые не следуют из ТЗ (выбор библиотеки, формат данных, отклонение от ТЗ), записываются в `docs/decisions/NNNN-<slug>.md` (шаблон — `docs/decisions/README.md`).
- Методы Telegram (Bot API, Mini Apps SDK) и API библиотек (Redux Toolkit, Fastify, Drizzle, grammY, nginx) сверяй с актуальной документацией (core.telegram.org, docs.telegram-mini-apps.com, redux-toolkit.js.org, fastify.dev, orm.drizzle.team, grammy.dev, nginx.org) перед реализацией, а не по памяти.

## Готовность задачи

Задача готова, когда выполнено всё:

1. Критерий «Готово» из ТЗ для этой задачи выполнен.
2. `npm run check` зелёный (типы + линтер + юнит-тесты).
3. Если менялся UI: `npm run e2e` зелёный, экран проверен в браузере в mock-режиме (субагент `ui-verifier`), скриншоты сохранены в `docs/screens/task-NN/`.
4. Субагент `spec-reviewer` не нашёл расхождений с ТЗ и этими правилами (или они исправлены).
5. В ТЗ отмечен чекбокс задачи, в `docs/progress.md` добавлена запись.
6. Изменения закоммичены в ветке задачи.

## Правила кода

- TypeScript strict, без `any` и `@ts-ignore`; если без них никак — комментарий с причиной.
- Контракт API — только zod-схемы из `packages/shared`; клиент и сервер импортируют их, а не дублируют типы.
- Схемы в `packages/shared` пишутся на `zod/mini` (`import { z } from 'zod/mini'`), чтобы клиентский бандл оставался маленьким; сервер использует те же схемы (решение 0002).
- Относительные импорты — с расширением (`./foo.ts`, `./App.tsx`), только стираемый синтаксис TypeScript (без `enum`, `namespace`, parameter properties): сервер и `packages/shared` запускаются Node 24 без сборки (решение 0002).
- Чистая бизнес-логика (алгоритм подбора, пересчёт порций, суммирование покупок, `overtook`) живёт в `packages/shared` и покрыта юнит-тестами.
- Сервер не доверяет клиенту: доступ, штампы, подписка — только на сервере. Клиент не подключается к базе: всё через API.
- Клиент обращается к бэкенду только через базовый URL из `VITE_API_URL`.
- Серверные данные на клиенте — через RTK Query (`src/api/`), не дублируются в слайсах; слайсы — для клиентского состояния (порции, таймеры, черновики).
- Все строки UI — в `src/i18n/ru.ts`. Никакого текста в JSX.
- Стили — классы Tailwind на токенах из `src/styles/index.css` (решение 0004): цвета, шрифты, размеры текста, радиусы и тени — только из `@theme`; палитра Tailwind по умолчанию отключена. Новый токен добавляется в `@theme` (проверь контраст текста ≥ 4.5:1), а не хардкодится в компоненте. Сначала ищи готовый компонент в `src/components/`.
- Интерактивные элементы — настоящие `button`/`input`/`label`, у иконок без подписи — `aria-label`, зоны нажатия от 44 × 44 px.
- У экранов с данными — состояния загрузки, ошибки и пустое.
- Методы Telegram SDK (`@tma.js/sdk-react`), которых может не быть в старом клиенте, — через проверку доступности SDK (`fn.isAvailable()` / `fn.ifAvailable()` / `fn.supports(...)`) и с запасным вариантом.
- Применённые миграции не редактируются — только новая миграция.

## Секреты и окружение

- Токен бота, пароль базы и ключ подписи ссылок — только в серверном окружении и `.env*` (в git не попадают). В клиентской сборке — только `VITE_*` без секретов.
- Агент не читает и не выводит содержимое `.env`, `.env.local` и подобных файлов; для примеров — `.env.example`.
- Агент не трогает VPS и прод: `ssh`, `scp`/`rsync` на сервер, деплой, миграции на проде, `git push` — только человек. Docker — только для локального окружения.

## Dev-режим

- `VITE_TG_MOCK=1` — подставное окружение Telegram (`src/telegram/mock/`), пользователь выбирается `?user=<id>` и запоминается во вкладке (sessionStorage); без параметра — 1002. Тестовые пользователи: `1001` новичок (нужен онбординг), `1002` 8 стран, `1003` 10 стран без подписки, `1004` 10 стран с подпиской, `1005` бот не может писать; друзья `2001`–`2003` (решение 0003).
- `VITE_API=mock` — MSW по фикстурам (`src/mocks/fixtures/`: 12 стран на 3 континентах, 36 блюд, 3 друга, состояния из ТЗ); фикстуры типизированы схемами из `packages/shared`. Новые эндпоинты — в `src/mocks/handlers.ts`.
- Ошибки и загрузка в моке: `?mock_error=auth` — первый запрос к эндпоинту `auth` отвечает 500 (`{error: {code: 'internal'}}`), повтор проходит; `?mock_error=auth:always` — падает всегда; несколько ключей — через запятую; `?mock_delay=<мс>` — задержка всех ответов. `page.route` в e2e запросы MSW не перехватывает, поэтому используйте эти параметры. Новые обработчики вызывают `takeFailure(controls, '<ключ>')` (`src/mocks/controls.ts`).
- Mock-код подключается только динамическим импортом под флагами в `src/main.tsx` и в продакшен-сборку не попадает; `mockServiceWorker.js` отдаёт dev-сервер из `node_modules/msw`.
- `VITE_API=local` — локальный Node-сервер и Postgres в Docker; initData подписывается тестовым токеном.
- `/dev/ui` — галерея токенов и базовых компонентов во всех вариантах (только `npm run dev`; ветка в `src/main.tsx` под `import.meta.env.DEV`).
- Проверка в браузере — вьюпорт 390 × 844 (iPhone 14), светлая тема.
