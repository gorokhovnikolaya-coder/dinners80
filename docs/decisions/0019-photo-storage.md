# 0019. Фото: загрузки, приватная папка `cooks` с `secure_link`, публичная `share`

Дата: 2026-10-17 · Задача: 17

## Контекст

Задача 17 — приём загрузок на сервер, приватная папка `cooks` с подписанными ссылками nginx (`secure_link`, 1 час) и публичная `share`. Критерий готовности: фото друга открывается, чужое — нет, просроченная ссылка не открывается, готовка без фото записывается.

ТЗ задаёт пути (`cooks/{user_id}/{uuid}.jpg`, `share/{uuid}.jpg`), лимиты 500 КБ и 2 МБ, срок ссылки 1 час. Не определены:
- где лежат файлы и откуда берётся ключ подписи;
- формат ссылки;
- проверка содержимого файла;
- защита диска от загрузок, которые так и не стали готовкой;
- в какой задаче делать `POST /uploads/share-card`.

Объём и лимит загрузок согласованы с пользователем 2026-10-17.

## Решение

- **Объём** (решение пользователя). В задаче 17:
  - `POST /uploads/cook-photo`, `POST /uploads/share-card`;
  - `PATCH /cooks/:id`;
  - проверка, что файл фото существует, в `POST /cooks`;
  - подписанные ссылки в `GET /friends/feed`;
  - nginx-шаблон для `/media/cooks/` и `/media/share/`.

  Canvas-карточка, `POST /share/stamp` и клиент шаринга — задача 20.
- **Хранилище** — `MEDIA_DIR` (абсолютный путь; по умолчанию `apps/server/media`, в `.gitignore`). Внутри `cooks/{user_id}/{uuid}.jpg` и `share/{uuid}.jpg`.
  - Имена создаёт сервер (`randomUUID`), имя файла из запроса не используется, запись с флагом `wx`.
  - Права 0644 и 0755: nginx в своём контейнере читает файлы под другим uid. Приватность обеспечивает nginx, а не права на диске.
  - Код — `apps/server/src/media/storage.ts`.
- **Ключ подписи** — `MEDIA_SIGNING_KEY`, обязателен, как `BOT_TOKEN`.
  - Не короче 32 символов, только `[A-Za-z0-9_-]`: nginx подставляет его в строку `secure_link_md5` как есть.
  - Тот же ключ получает nginx через `envsubst` официального образа.
- **Ссылка** — формат модуля `secure_link` (nginx.org):
  - вид: `${MEDIA_URL}/cooks/{user_id}/{uuid}.jpg?md5=<md5>&expires=<unix>`;
  - `md5` — MD5 строки `"$expires$uri <key>"` в base64url без `=`; `$uri` — путь из `MEDIA_URL`, например `/media/cooks/…`;
  - срок — ровно час с момента выдачи;
  - IP в подпись не входит: в Telegram у пользователя меняется сеть.
  - Код — `apps/server/src/media/signedLink.ts`. Юнит-тест сверяет хеш с примером документации nginx.
- **nginx** — `deploy/nginx/templates/media.conf.template`, location-блоки для `server` домена (полный `nginx.conf` — задача 23).
  - Рендерится в `/etc/nginx/media.conf` (`NGINX_ENVSUBST_OUTPUT_DIR=/etc/nginx`), чтобы не попасть в `conf.d` на уровне `http`.
  - `/media/cooks/`: неверная или отсутствующая подпись — `403`, просроченная — `410`, `Cache-Control: private, max-age=3600`.
  - `/media/share/`: без подписи, `public, max-age=86400`.
  - Листинг каталогов выключен.
  - Файлы смонтированы в `/srv/media`.
- **Загрузки** — `@fastify/multipart` в отдельной области Fastify, только для двух маршрутов.
  - Один файл, без других полей, поле `photo` или `card`. Не multipart — `400`.
  - Размер ограничивается при чтении потока: больше 500 КБ или 2 МБ — `413 validation`.
  - Содержимое проверяется по сигнатуре JPEG `FF D8 FF`, иначе `400`. Перекодирования нет: сжимает клиент (решение 0010).
- **Лимит загрузок фото готовок** (решение пользователя) — `COOK_PHOTO_UPLOADS_PER_DAY_LIMIT` = 40 за 24 часа на пользователя, сверх — `429 rate_limited`.
  - Считается по времени файлов в папке пользователя, отдельной таблицы нет.
  - Подсчёт и запись идут по очереди в пределах пользователя, поэтому параллельные запросы не проходят лимит (тест). Очередь живёт в памяти одного процесса сервера.
  - Карточки `share` не лимитируются: их удаляет воркер через 30 дней (задача 21).
- **Осиротевшие фото** (загружены, готовка не записана) пока не удаляются (решение пользователя) — пункт в «Заметках» `docs/progress.md`.
- **`POST /cooks`** — фото принимается из своей папки и только если файл существует, иначе `400 validation`.
- **`PATCH /cooks/:id`** — «добавляет фото к уже записанной готовке».
  - Только своя готовка: чужая или не-uuid — `404`.
  - Только если фото ещё нет, иначе `400 validation`: фото не заменяется.
  - Фото — по тем же правилам, что в `POST /cooks`.
  - Ответ — `{cookId, photoPath}`. В интерфейсе MVP не используется, поэтому в мок не добавлен.
- **Ссылки в ответах API** — `GET /friends/feed` подписывает `photoUrl` штампов друзей. Лента строится только по друзьям, поэтому подписанной ссылки на фото чужого пользователя API не выдаёт. Свои фото автору в MVP не показываются, полей для них в API нет.
- **`POST /uploads/share-card`** отвечает `{url}` = `${MEDIA_URL}/share/{uuid}.jpg`. Схема — `uploadShareCardResponseSchema`. В моке отвечает тем же путём, файла за ним нет — показ в моке решит задача 20.
- **Режим `VITE_API=local`** — dev-сервер Vite отдаёт `/media/share/*` и `/media/cooks/*` из `MEDIA_DIR` с той же проверкой подписи (`checkSecureLink` в `apps/web/localApi.ts`, юнит-тест на пример nginx и срок). Нужен `MEDIA_SIGNING_KEY` в `.env`. Загрузка фото на экране «Фото и штамп» в режиме local теперь работает.
- **Тесты.**
  - Юнит: подпись, хранилище, конфиг, `checkSecureLink`, схемы, MSW `share-card`.
  - `npm run test:db`: загрузки, лимит, `POST /cooks` с фото и без, `PATCH`, ссылки в ленте.
  - `npm run test:nginx` (Docker, `nginx:1.28-alpine`): ссылка, подписанная кодом сервера, открывает фото; без подписи, с подписью другого файла и с чужим ключом — `403`; просроченная — `410`; `share` открыт, листинг закрыт.

## Альтернативы

- **Отдавать фото через Node с проверкой прав на каждый запрос.** Нагружает сервер, а ТЗ прямо выбирает `secure_link`.
- **Подписывать с IP клиента** (`$remote_addr`). Ссылка ломалась бы при смене сети (Wi-Fi ↔ мобильная), а NAT операторов ничего не добавляет к защите.
- **Округлять срок до часовой границы для кеширования.** Ссылка жила бы меньше часа. Лента и так кешируется RTK Query, а картинки — браузером по полному URL.
- **Перекодировать фото на сервере (sharp).** Тяжёлая нативная зависимость. Клиент уже сжимает, сигнатура и размер проверяются.
- **Таблица загрузок для лимита.** Лишняя миграция. Для MVP с одним процессом сервера хватает подсчёта по файлам.

## Последствия

- В окружение сервера (локально — `.env`, на VPS — секреты compose) нужно добавить `MEDIA_SIGNING_KEY`, при необходимости `MEDIA_DIR`. Образец в `.env.example` добавляет человек (правка `.env*` закрыта хуком).
- Задача 20: `shareToStory` нужен абсолютный публичный URL. Если `MEDIA_URL` относительный (`/media`), клиент дополняет его `location.origin`, либо `MEDIA_URL` на проде задаётся абсолютным.
- Задача 21: воркер удаляет `share/*` старше 30 дней. Там же можно удалять осиротевшие фото `cooks`, если пользователь решит.
- Задача 23: nginx-контейнер монтирует `MEDIA_DIR` в `/srv/media` (только чтение), получает `MEDIA_SIGNING_KEY` и `NGINX_ENVSUBST_OUTPUT_DIR=/etc/nginx` и включает `media.conf` в `server`. В бэкап входит `MEDIA_DIR`.
