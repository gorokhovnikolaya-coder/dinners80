# 0021. Оплата в Stars: счёт, вебхук, продления и возвраты

Дата: 2026-10-17 · Задача: 19

## Контекст

ТЗ («Оплата в Stars», «Модель данных») задаёт:
- `createInvoiceLink` в `XTR` с пустым `provider_token`; месяц — подписка на 30 дней, год — разовый платёж на 365 дней;
- `pre_checkout_query` проверяет тариф и пользователя, `successful_payment` записывает подписку идемпотентно по `telegram_payment_charge_id`;
- продление — новая запись: `starts_at` = окончание предыдущего периода, `expires_at` — из `subscription_expiration_date`;
- покупка при действующей подписке начинается после её окончания;
- возврат — `refundStarPayment` вручную, запись получает `refunded`;
- `payment_success` пишет сервер.

ТЗ не определяет:
- тексты счёта и отказов;
- формат `invoice_payload`;
- что делать со второй месячной подпиской: Bot API разрешает пользователю несколько одновременных подписок, и Stars списывались бы дважды;
- как администратору делать возврат;
- нужно ли сообщение бота после оплаты.

Продуктовые вопросы согласованы с пользователем 2026-10-17: приняты все рекомендации исполнителя.

## Решение

**Тексты** (`apps/server/src/bot/texts.ts`):
- счёт месяца: «Подписка на месяц» / «Все страны «Вокруг света за 80 ужинов». Продлевается каждые 30 дней, отключить можно в настройках Telegram.»;
- счёт года: «Подписка на год» / «Все страны «Вокруг света за 80 ужинов» на 365 дней. Разовый платёж без автопродления.»;
- в счёте нет фото, подпись цены совпадает с названием.

Отказы `pre_checkout_query` (их показывает Telegram):
- «Счёт устарел. Откройте оплату в приложении ещё раз.» — payload не наш, валюта не `XTR`, сумма не равна текущей цене тарифа или пользователя нет;
- «Этот счёт выставлен другому пользователю. Откройте оплату в приложении.» — `from.id` не совпадает с `tg_id` пользователя из payload (ссылку переслали);
- «Подписка уже оформлена.» — месячный счёт при действующей месячной подписке.

После оплаты бот ничего не отправляет: Telegram сам показывает служебное сообщение, клиент ведёт пользователя дальше (решение 0014).

**`invoice_payload`** — `<plan>:<user uuid>` (ASCII, не больше 128 байт). `invoicePayload`, `parseInvoicePayload` и `planByStars` живут в `packages/shared/src/payments.ts`.

**`POST /api/payments/invoice`** (`routes/payments.ts`) вызывает `createInvoiceLink` через `Api` grammY. `Api` создаётся всегда, даже без `WEBAPP_URL`. Цена берётся из `SUBSCRIPTION_PRICES_STARS`. Для месяца добавляется `subscription_period: 2592000` — Telegram разрешает только 30 дней и цену подписки до 10000 Stars.
- Месячный счёт при действующей месячной подписке → `409 conflict`. Код ошибки `conflict` добавлен в `API_ERROR_CODES`.
- Годовой счёт разрешён и при действующей подписке (ТЗ).
- Ошибка Bot API → 500: клиент показывает «Не удалось открыть оплату».

**«Действующая месячная»** (`hasActiveMonth`) — запись `plan = 'month'`, `status = 'active'`, `expires_at > now()`. Каждая месячная покупка — подписка Telegram, поэтому её наличие и значит автопродление. Если пользователь отключил продление в Telegram, новый месяц он сможет купить только после окончания периода. Пейвол при активной подписке тарифы и так не показывает.

**`successful_payment`** (`db/payments.ts`, `recordPayment`) выполняется одной транзакцией:
- строка пользователя блокируется (`for update`), чтобы параллельные платежи одного пользователя корректно выстраивались друг за другом;
- пользователь берётся из payload, если его `tg_id` совпадает с плательщиком, иначе — по `tg_id` плательщика;
- тариф берётся из payload, если сумма равна его цене, иначе — по сумме (`planByStars`). Stars уже списаны, поэтому платёж записывается в любом случае. Неизвестный плательщик не записывается, сервер пишет ошибку в лог, апдейт получает 200;
- период считается функцией `paymentPeriod`:
  - начало — окончание действующей подписки или текущий момент (`subscriptionPeriod`);
  - если есть `subscription_expiration_date`, период заканчивается этой датой. Так продление сдвигает `expires_at` на дату Telegram;
  - исключение: дата Telegram больше чем на сутки раньше полного периода от начала. Так бывает, когда месяц выстроен после года, и тогда период — полные 30 дней, чтобы оплаченный месяц не урезался. Сутки допуска покрывают задержку доставки апдейта;
- `insert … on conflict (telegram_payment_charge_id) do nothing`: при повторе вебхука нет ни второй записи, ни второго события;
- `is_recurring` — продление: `is_recurring && !is_first_recurring`. Первый платёж месячной подписки продлением не считается;
- `payment_success {plan, stars_amount, is_recurring}` пишется в той же транзакции и только при новой записи.

**Возвраты**:
- вебхук `refunded_payment` идемпотентно ставит `refunded` (`markRefunded`), поэтому возврат любым способом закрывает доступ;
- `npm run payments:refund -- <telegram_payment_charge_id>` (`bot/refundCli.ts`, логика — `bot/refund.ts`) запускает человек:
  - для месяца сначала `editUserStarSubscription(is_canceled = true)`, чтобы следующий период не списался. Если Telegram отказал, возврат продолжается, а скрипт просит проверить подписку вручную;
  - затем `refundStarPayment`; ответ `CHARGE_ALREADY_REFUNDED` считается успехом;
  - запись получает `refunded`;
  - повторный запуск сообщает «уже возвращён».

**`bot:setup`**: `allowed_updates` = `message`, `my_chat_member`, `pre_checkout_query`. `successful_payment` и `refunded_payment` приходят как сообщения.

**Dev-режим**:
- мок (`VITE_API=mock`) не менялся — решение 0014;
- в `VITE_API=local` счёт создаётся настоящим Bot API по `BOT_TOKEN` из `.env`, но вебхук локально не приходит: платёж проверяется только на сервере с https.

## Альтернативы

- Разрешать любую месячную покупку (ТЗ буквально). Это ведёт к двойному списанию: Telegram продлевает обе подписки.
- `expires_at` всегда из `subscription_expiration_date`. Месяц, купленный во время года, давал бы период меньше 30 дней или нарушал `check expires_at > starts_at`.
- `expires_at = max(дата Telegram, начало + 30 дней)`. Задержка доставки каждого апдейта сдвигала бы срок от даты Telegram.
- Только скрипт возврата без `refunded_payment`. Тогда возврат, сделанный не скриптом, не закрыл бы доступ.
- Хранить payload счёта в базе. Это лишняя таблица: проверка по тарифу, цене и пользователю не требует хранить выданные счета.

## Последствия

- После мёржа человек запускает `npm run bot:setup` повторно (новый `allowed_updates`), затем проверяет оплату в тестовой среде Telegram.
- Не проверено на реальном Telegram:
  - что для автопродлений `pre_checkout_query` не приходит. Если придёт — отказ «Подписка уже оформлена» сорвёт продление, и проверку `already_subscribed` нужно будет снять;
  - какой `telegram_payment_charge_id` принимает `editUserStarSubscription` для продлений.
- Обновление Bot API `subscription` (`BotSubscriptionUpdated`: canceled / active / failed, июль 2026) не обрабатывается: доступ и так кончается по `expires_at`. Пригодится, если понадобится показывать «продление отключено».
- Задача 22 (события): `payment_success` уже пишется вебхуком.
