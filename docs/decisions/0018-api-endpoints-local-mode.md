# 0018. API: эндпоинты ядра и режим `VITE_API=local`

Дата: 2026-10-16 · Задача: 16

## Контекст

Задача 16 — «остальные эндпоинты из раздела API», готово, когда фронтенд работает в режиме `VITE_API=local` без MSW. Таблица API в ТЗ шире задачи: часть эндпоинтов относится к задачам 17–22.

ТЗ не определяет:
- как клиент в браузере получает подписанную initData;
- откуда берутся фото контента;
- как проверить состояния тестовых пользователей на локальной базе.

Объём и сид тестовых пользователей согласованы с пользователем 2026-10-16.

## Решение

- **Объём** (решение пользователя). В задаче 16 сделано ядро:
  - `PATCH /me`, `GET /home`, `GET /dishes/:id`, `GET /map`, `POST /cooks`;
  - `GET /friends/leaderboard`, `GET /friends/feed`;
  - `GET /shopping`, `POST /shopping`, `PATCH /shopping/:id`, `DELETE /shopping/checked`.

  Остальное — в своих задачах: загрузки фото и `PATCH /cooks/:id` — 17, бот — 18, счёт и вебхук оплаты — 19, share — 20, `POST /events` — 22. В режиме local «Сфотографировать» пока показывает «Не удалось загрузить фото» (готовка записывается без фото), пейвол — «Не удалось открыть оплату».
- **Логика — общая с моком.** Сервер вызывает те же функции `packages/shared`, что и MSW-обработчики: `suggestDishes`, `buildPassport`, `buildLeaderboard`, `latestFriendStamps`, `findOvertakenFriend`, `dishLabel`, `scaleAmount`, `applyProfilePatch`. Запросы к базе — в `src/db/content.ts` и `src/db/cooks.ts`, маршруты — в `src/routes/*.ts`, по одной функции регистрации на группу. Тело и query проверяются схемами shared (`parseOr400` → `400 validation`).
- **Контент.**
  - Сервер видит только опубликованные страны и блюда (`is_published`): неопубликованное блюдо — `404`.
  - Счётчик стран (`countriesCount` в `/home`, `/map`, `POST /cooks`) считает только опубликованные страны, чтобы N не превышал знаменатель.
  - `dishesCount` — все готовки.
  - Лента и рейтинг друзей берут все готовки.
  - Контент читается из базы на каждый запрос: 90 блюд, кеш в MVP не нужен.
- **Доступ.** SQL-функция `has_access` проверяется в `GET /dishes/:id` (`403 paywall` с превью), в `POST /cooks` и `POST /shopping` (`403 paywall`). Замки на главном и карте ставят функции shared по той же формуле, подписка — `subscriptionStatus`.
- **`POST /cooks`** — одна транзакция с `pg_advisory_xact_lock` по пользователю. Порядок:
  1. Лимит — 20 записей за последние 24 часа (решение 0010), иначе `429 rate_limited`.
  2. Доступ.
  3. Вставка.
  4. Счётчики до и после, «обогнал» среди друзей.

  Параллельные запросы не проходят лимит (тест). Фото принимается только с путём `cooks/{user_id}/…`, иначе `400 validation`. В `cooks.photo_path` путь пишется без `cooks/` (`{user_id}/{uuid}.jpg`, как в ТЗ). Существование файла проверит задача 17.
- **Лента друзей:** `photoUrl` пока `null` — подписанные ссылки `secure_link` появятся в задаче 17.
- **Покупки.**
  - `POST` удаляет некупленные позиции блюда и вставляет новые в одной транзакции. Неизвестный `key` — `400`, закрытая страна — `403`.
  - `PATCH` чужой или не-uuid позиции — `404`.
  - Количества пересчитываются при чтении (`scaleAmount` на `servings` позиции).
- **Фото контента.** `imageUrl` = `${MEDIA_URL}/content/<image_path>`, `MEDIA_URL` по умолчанию `/media` (`config.ts`). В проде `/media/content/` будет раздавать nginx (задача 23). В dev их отдаёт Vite из `content/`; фото нет — `404`.
- **Режим `VITE_API=local`** (`apps/web/localApi.ts`, плагин Vite только для `serve`).
  - `/api` проксируется на `127.0.0.1:$PORT`.
  - Mock-окружение Telegram (`VITE_TG_MOCK=1`) по-прежнему строит initData с заглушкой `hash`. Прокси в Node убирает `hash` и `signature`, ставит свежий `auth_date` и подписывает данные токеном `BOT_TOKEN` из `.env` тем же алгоритмом, что сервер (юнит-тест сверяет хеш с серверным `signInitData`).
  - Токен не попадает ни в браузер, ни в сборку. Без `BOT_TOKEN` dev-сервер в режиме local не стартует с понятной ошибкой.
- **Тестовые пользователи** (решение пользователя) — `npm run db:seed:dev` (`apps/server/seed/devUsers.ts`).
  - Работает только с localhost (та же проверка, что у `db:reset`).
  - В одной транзакции удаляет пользователей с `tg_id` фикстур (каскадом — их данные) и загружает из мок-фикстур `apps/web/src/mocks/fixtures`: профили с теми же uuid, готовки (даты относительно запуска), дружбу в обе стороны, подписки (`dev-fixture-<tg_id>`; закончившаяся — `expired`) и списки покупок (ингредиент — по `dish_id` и `key`).
  - Id блюд фикстур совпадают с `content/`.
  - Чтобы сервер типизировал фикстуры, пять файлов фикстур включены в `apps/server/tsconfig.json` (`rootDir: ../..`). Они импортируют только `@tma80/shared`.
- **Тесты.** `apps/server/src/routes/api.test.ts` гоняет все эндпоинты ядра на локальной базе с контентом (`npm run test:db`, в `check` пропускается). `devUsers.test.ts` и `localApi.test.ts` — обычные юнит-тесты.

## Альтернативы

- **Подписывать initData в браузере** токеном из `VITE_*` — токен попал бы в клиентскую сборку.
- **Dev-эндпоинт сервера, выдающий подписанную initData**, — риск оставить его включённым на проде.
- **Сид тестовых пользователей внутри `db:reset`** — `db:reset` должен давать чистую базу с одним контентом. Тестовые данные — отдельной командой.
- **Перенести фикстуры в `packages/shared`** — они нужны только моку и dev-сиду. Переносить их в общий пакет (и в клиентский граф импортов) ради одного скрипта не стоит.

## Последствия

- Задача 17:
  - `POST /uploads/cook-photo` и `PATCH /cooks/:id`;
  - подписанные ссылки на фото в ленте (`photoUrl`): путь в базе — `{user_id}/{uuid}.jpg`;
  - проверка, что файл фото существует, в `POST /cooks`.
- Задача 18: в режиме local mock-окружение Telegram не сообщает серверу о `requestWriteAccess` (в моке это делает MSW). Флаг `bot_can_write` поставит вебхук бота.
- Задача 19: `POST /payments/invoice`. До неё пейвол в режиме local показывает ошибку счёта.
- Задача 23: nginx раздаёт `/media/content/` из копии фото контента. Если фото на другом домене — `MEDIA_URL` в окружении сервера.
- `.env.example`: можно добавить `MEDIA_URL=/media` (агенту правка `.env*` закрыта хуком).
