# 0020. Бот: вебхук, команды, приглашения и `bot_can_write`

Дата: 2026-10-17 · Задача: 18

## Контекст

ТЗ задаёт:
- команды бота `/start` (с параметром — плюс приглашение), `/terms`, `/paysupport`;
- кнопку меню;
- вебхук `POST /bot/webhook` с проверкой `X-Telegram-Bot-Api-Secret-Token`;
- когда `bot_can_write` становится true;
- что напоминания по умолчанию включены у тех, кто нажал `/start`.

ТЗ не определяет:
- тексты бота;
- откуда брать секрет вебхука;
- как бот создаёт пользователя;
- что считать «новым» пользователем, если он сначала пришёл в бота;
- как понять, что `/start` первый;
- что делать с блокировкой бота до рассылки (задача 21).

Продуктовые вопросы согласованы с пользователем 2026-10-17: приняты все рекомендации исполнителя.

## Решение

**Тексты** (`apps/server/src/bot/texts.ts`). Сообщения отправляются без `parse_mode`, поэтому имена пользователей не нужно экранировать.
- `/start` и любой другой текст: «Привет! Здесь вы готовите ужины из кухонь разных стран и собираете штампы в паспорт. Откройте приложение — подберём ужин на сегодня.» и web_app-кнопка «Открыть».
- `/start <код>` с чужим действующим кодом: «<Имя> зовёт вас в «Вокруг света за 80 ужинов». Вы уже друзья в рейтинге — готовьте и соревнуйтесь!» и «Открыть». Неверный или собственный код — как `/start`.
- `/terms`: «Условия использования: <TERMS_URL>» и «Политика конфиденциальности: <PRIVACY_URL>» (только заданные). Без адресов — «Условия использования появятся до запуска оплаты.»
- `/paysupport`: «По вопросам оплаты напишите <SUPPORT_CONTACT> — ответим и при необходимости вернём Stars.» Без контакта — «Контакт поддержки по оплате появится до запуска оплаты.»
- Кнопка меню — «Открыть».
- Команды: start — «Открыть приложение», terms — «Условия использования», paysupport — «Помощь с оплатой».

**Вебхук** — `POST /api/bot/webhook`, `config.auth: 'public'`, адаптер grammY `webhookCallback(bot, 'fastify', { secretToken })`.
- Неверный или отсутствующий секрет → `401 unauthorized`. Хук маршрута сравнивает секрет за постоянное время до разбора апдейта и до первого `getMe`, который grammY делает при первом апдейте; grammY потом проверяет секрет ещё раз.
- Ошибка базы или Bot API → 500, Telegram повторит апдейт.
- Ответ 403 на отправку (бот заблокирован) сбрасывает `bot_can_write` и не считается ошибкой.
- Бот обслуживает только личные чаты.
- Вебхук регистрируется, только если задан `WEBAPP_URL` (https-адрес мини-аппа для web_app-кнопок). Без него сервер стартует с предупреждением: так работает локальная разработка.

**Секрет вебхука** — `HMAC-SHA256(key = "tma80-bot-webhook", data = BOT_TOKEN)` в hex, 64 символа (`bot/secret.ts`). Отдельной переменной нет: сервер и `bot:setup` вычисляют одно и то же значение, и оно меняется вместе с токеном.

**`npm run bot:setup`** (`bot/setup.ts`) запускает человек на реальном боте. Скрипт:
- вызывает `setWebhook` на `${PUBLIC_URL}/api/bot/webhook` с `secret_token` и `allowed_updates: ['message', 'my_chat_member']`. В задаче 19 добавится `pre_checkout_query`, после неё скрипт нужно запустить повторно;
- вызывает `setMyCommands`;
- вызывает `setChatMenuButton` (web_app «Открыть», `WEBAPP_URL`).

Повторный запуск безопасен.

**`/start`** — одна транзакция (`db/users.ts`, `startBot`):
- upsert по `tg_id`: имя и username из `from`, фото нет — его заполнит `POST /auth`;
- `bot_can_write = true`;
- при первом `/start` (`users.bot_started_at` пуст) — `reminder_enabled = true` и запись `bot_started_at`. Повторный `/start` выбор пользователя не меняет. Новая колонка `bot_started_at`, миграция `0002_bot_started`;
- с кодом — то же приглашение, что в `POST /auth`.

**Приглашение** (`applyInvite`, общее для `POST /auth` и `/start <код>`):
- чужой известный код → дружба в обе стороны;
- `invited_by` и `invite_joined` получает пользователь, у которого ещё нет `invited_by` и не пройден онбординг. Так, пришедший сначала в бота и открывший потом ссылку друга, тоже считается приглашённым. Это уточняет решение 0017;
- условие проверяется в самом `update … where invited_by is null and onboarded_at is null`, поэтому из параллельных входов событие пишет только один.

**`bot_can_write`**:
- `/start` → true;
- сервисное сообщение `write_access_allowed` → true;
- `my_chat_member`: `kicked` → false, `member` → true;
- ответ 403 → false.

Неизвестный пользователь в этих апдейтах игнорируется. Сброс по 403 при рассылке — задача 21.

**Dev-режим**: `?startapp=<код>` в mock-окружении Telegram кладёт `start_param` в initData (и `tgWebAppStartParam`). MSW-обработчик `POST /auth` создаёт дружбу (мок-БД, sessionStorage). В режиме `VITE_API=local` прокси переподписывает initData вместе с `start_param`. Коды тестовых пользователей — `inv<tg_id>`, например `?user=1001&startapp=inv1002`.

## Альтернативы

- Отдельная переменная `BOT_WEBHOOK_SECRET`. Это ещё один секрет, который нужно держать в `.env` и синхронно передавать в `setWebhook`; производный от токена ничем не хуже.
- `/start <код>` без записи дружбы в боте: только кнопка `t.me/<бот>/<app>?startapp=<код>`. Пользователь, создавший себя в боте, тогда не считался бы приглашённым.
- Включать напоминание при каждом `/start` или при `bot_can_write = false`. Первое затирает выбор пользователя после «Перезапустить», второе не включает напоминание тем, кто пришёл с `allows_write_to_pm`.

## Последствия

- Новые серверные переменные: `WEBAPP_URL`, `PUBLIC_URL` (только `bot:setup`), `TERMS_URL`, `PRIVACY_URL`, `SUPPORT_CONTACT` — нужно добавить в `.env.example` (человек).
- Задача 19 добавляет в бота `pre_checkout_query` и `successful_payment` и расширяет `allowed_updates`.
- Задача 21 при 403 в рассылке использует `setBotCanWrite(db, tgId, false)`.
- Задача 22: `app_open` с источником — `start_param` уже доступен в initData.
